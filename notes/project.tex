\begin{abstract}
\noindent This study guide walks through the \texttt{vit-jax-distributed-scaling}
project: training a Vision Transformer on CIFAR-100 with JAX/Flax, parallelised via
\texttt{jax.pmap}, and using the setup to investigate two systems questions ---
\emph{how does throughput scale with device count?} and \emph{how badly does a single
slow worker hurt synchronous training?}. Every section pairs intuition with the code
that implements it, and ends with exercises, predictions, and labs for you to work through.
\end{abstract}

\section{What we are building, and why}
% =========================================================================

\begin{objectives}
By the end of this section you should be able to:
\begin{itemize}[leftmargin=*, itemsep=1pt]
    \item explain in one sentence what data-parallel training is;
    \item name the two systems phenomena this project is designed to measure;
    \item locate every module in the repo and say what it owns.
\end{itemize}
\end{objectives}

A Vision Transformer trains by (a)~splitting an image into patches, (b)~treating those
patches as a token sequence, and (c)~feeding the sequence through a stack of transformer
blocks. Training one on a single accelerator is unremarkable; training one
\emph{across} accelerators exposes two phenomena that matter far beyond ViT:

\begin{keypoint}[Two phenomena we care about]
\textbf{(1) The all-reduce barrier.} Every device must reach the gradient-averaging step
before any device can proceed. This is the single most important synchronisation primitive
in data-parallel training, and it is what makes distributed training brittle to slow workers.

\textbf{(2) Scaling efficiency.} Doubling the devices never exactly doubles throughput,
because gradients have to travel between them. Measuring how much you lose is how you
diagnose whether your distributed strategy is working.
\end{keypoint}

\noindent We choose ViT-Small on CIFAR-100 because the model is small enough
($\sim$9.5M parameters) that per-step compute is short --- and short per-step compute is
precisely what makes the all-reduce cost \emph{visible} relative to forward/backward time.
With a bigger model, compute hides everything we want to see.

% =========================================================================

\subsection{Images as sequences}

Transformers are sequence models. To feed them an image we must turn the image
\emph{into} a sequence:

\begin{enumerate}
\item Tile the $32 \times 32$ image into non-overlapping $4 \times 4$ patches, giving $64$ patches.
\item Flatten each patch and project it through a learnable linear layer to get a 384-dim token.
\item Prepend a learnable \texttt{[CLS]} token (so 65 tokens total).
\item Add learnable positional embeddings (the model cannot recover spatial position otherwise).
\end{enumerate}

The output is a tensor of shape $(B, 65, 384)$: a batch of 65-token sequences.
From here on it is a pure Transformer encoder.

\end{exercise}

\subsection{Pre-norm transformer blocks}

Each block is:
$$x' = x + \text{Attn}(\text{LN}(x)), \qquad x'' = x' + \text{MLP}(\text{LN}(x'))$$

\begin{keypoint}[Pre-norm stabilises deep stacks]
Applying LayerNorm \emph{before} attention and MLP (rather than after) keeps the residual
stream at unit scale regardless of depth. Post-norm variants train fine up to $\sim$12
layers but tend to need careful warmup at higher depth; pre-norm trains predictably at
100+ layers.
\end{keypoint}

\subsection{Classification head}

After $N$ transformer blocks and a final LayerNorm, we read out the \texttt{[CLS]} token only
(\texttt{x[:, 0]}) and feed it through a linear layer to 100 logits. Over $N$ rounds of
self-attention, the CLS token has aggregated information from every patch, making it a
learned summary of the whole image.

\subsection{Code: patch embedding}

\begin{lstlisting}[style=py]
class PatchEmbedding(nn.Module):
    hidden_dim: int = 384
    patch_size: int = 4
    image_size: int = 32

    @nn.compact
    def __call__(self, x):
        B = x.shape[0]
        N = (self.image_size // self.patch_size) ** 2    # number of patches
        # (B, H, W, C) -> (B, N, patch*patch*C) -> (B, N, hidden_dim)
        x = nn.Dense(self.hidden_dim, name="patch_projection")(
            x.reshape(B, self.image_size // self.patch_size, self.patch_size,
                         self.image_size // self.patch_size, self.patch_size, -1)
             .transpose(0, 1, 3, 2, 4, 5)
             .reshape(B, N, -1))
        cls = self.param("cls_token",    nn.initializers.normal(0.02), (1, 1, self.hidden_dim))
        pos = self.param("pos_embedding", nn.initializers.normal(0.02), (1, N + 1, self.hidden_dim))
        x   = jnp.concatenate([jnp.broadcast_to(cls, (B, 1, self.hidden_dim)), x], axis=1)
        return x + pos
\end{lstlisting}

\section{Data pipeline}
% =========================================================================

\begin{objectives}
\begin{itemize}[leftmargin=*, itemsep=1pt]
    \item explain why we skip \texttt{tf.data} and use an in-memory numpy iterator;
    \item compute the shape of a sharded batch;
    \item describe how random crop with reflection padding differs from simple random crop.
\end{itemize}
\end{objectives}

CIFAR-100 is 50{,}000 training images, $32 \times 32 \times 3$ each. Standardised and stored
as float32:
$$50{,}000 \times 32 \times 32 \times 3 \times 4 \text{ bytes} \approx 614 \text{ MB}.$$
The full dataset fits comfortably in RAM, so we bypass \texttt{tf.data} entirely:

\begin{lstlisting}[style=py]
def _numpy_data_iterator(images, labels, batch_size, shuffle, augment, loop, seed):
    n      = images.shape[0]
    usable = (n // batch_size) * batch_size          # drop the ragged tail
    rng    = np.random.RandomState(seed)
    while True:
        idx = np.arange(n)
        if shuffle: rng.shuffle(idx)
        idx = idx[:usable]
        for s in range(0, usable, batch_size):
            batch_idx  = idx[s : s + batch_size]
            batch_imgs = images[batch_idx].copy()
            if augment:
                batch_imgs = _augment_batch(batch_imgs, rng)
            yield {"image": batch_imgs, "label": labels[batch_idx]}
        if not loop: break
\end{lstlisting}

\textbf{Augmentation} is random horizontal flip plus random crop with 4-pixel reflection
padding. Both are vectorised with advanced indexing over the whole batch --- no per-image
Python loops.

\subsection{Sharding for pmap}

Each distributed step needs each device's private slice of the global batch. We reshape
$(B, H, W, C) \to (\text{num\_devices}, B/\text{num\_devices}, H, W, C)$:

\begin{lstlisting}[style=py]
def shard_batch(batch, num_devices):
    def reshape(x):
        per_device = x.shape[0] // num_devices
        return x.reshape((num_devices, per_device) + x.shape[1:])
    return {k: reshape(v) for k, v in batch.items()}
\end{lstlisting}

A global batch of 512 across 8 devices means each device sees 64 images per step.

\subsection{SPMD and pmap}

\begin{keypoint}[SPMD in one line]
\textbf{S}ingle \textbf{P}rogram, \textbf{M}ultiple \textbf{D}ata: you write one function, and
pmap arranges for it to run on every device simultaneously, each receiving its own slice of
the input.
\end{keypoint}

\begin{lstlisting}[style=py]
@partial(jax.pmap, axis_name="batch", devices=devices)
def train_step(state, batch, rng):
    ...
\end{lstlisting}

Two rules worth internalising:

\begin{enumerate}
\item Inputs must have a leading axis of size \texttt{len(devices)}; pmap strips this axis
      and hands device~$i$ the $i$-th slice.
\item Outputs \emph{retain} a leading device axis. To read a scalar on the host you index
      \texttt{value[0]} --- any entry works when the value was \texttt{pmean}'d, since every
      device then holds the same number.
\end{enumerate}

\subsection{All-reduce via pmean}

After each device has computed its local gradients from its slice of the batch, we
\emph{average} those gradients across every device. That averaging is an \textbf{all-reduce},
and it is what makes the whole pipeline mathematically equivalent to training on one device
with the full global batch.

\begin{lstlisting}[style=py]
grads = jax.lax.pmean(grads, axis_name="batch")   # the all-reduce
loss  = jax.lax.pmean(loss,  axis_name="batch")
acc   = jax.lax.pmean(acc,   axis_name="batch")
new_state = state.apply_gradients(grads=grads)
\end{lstlisting}

\begin{keypoint}[The barrier]
\texttt{pmean} is a \textbf{collective} operation: it cannot complete on any single device
until every device has contributed its value. Every training step therefore has an implicit
synchronisation barrier. Slow workers hold up fast ones. This is the mechanism the
\textbf{straggler experiment} isolates.
\end{keypoint}

Schematically, one training step looks like:

\begin{lstlisting}[style=sh]
Device 0: forward -> backward -> [pmean] -> optimizer step
Device 1: forward -> backward -> [pmean] -> optimizer step
Device 2: forward -> backward -> [pmean] -> optimizer step
Device 3: forward -> backward -> [pmean] -> optimizer step
                                    ^
                           all-reduce barrier:
                           nobody moves until everybody arrives
\end{lstlisting}

\subsection{Train state and replication}

Flax's \texttt{TrainState} bundles the model's apply function, parameters, and optimizer
state. We build one master copy, then replicate it across every device:

\begin{lstlisting}[style=py]
def create_train_state(rng, model, lr, image_size, weight_decay, warmup_steps, total_steps):
    dummy  = jnp.ones([1, image_size, image_size, 3])
    params = model.init(rng, dummy, train=False)["params"]

    # Clamp warmup so short runs don't violate decay_steps > warmup_steps.
    effective_warmup = min(warmup_steps, max(1, total_steps // 2))
    schedule = optax.warmup_cosine_decay_schedule(
        init_value=0.0, peak_value=lr,
        warmup_steps=effective_warmup, decay_steps=total_steps, end_value=0.0)
    tx = optax.adamw(learning_rate=schedule, weight_decay=weight_decay)
    return TrainState.create(apply_fn=model.apply, params=params, tx=tx)

state = replicate_state(state, devices=devices)
\end{lstlisting}

\begin{pitfall}[The warmup-vs-total-steps bug]
\texttt{optax.warmup\_cosine\_decay\_schedule} assumes \texttt{decay\_steps > warmup\_steps};
if it is not, you get \texttt{ValueError: decay\_steps=-306}. A 2-epoch smoke test runs
only 194 steps, far short of the default 500-step warmup, so we clamp
\texttt{effective\_warmup} to \texttt{total\_steps // 2}. Long runs still use the intended
warmup; short runs self-adjust.
\end{pitfall}

\end{exercise}

\section{The training loop}
\label{sec:training-loop}
% =========================================================================

\begin{objectives}
\begin{itemize}[leftmargin=*, itemsep=1pt]
    \item trace a single training step from batch fetch to parameter update;
    \item identify where the implicit host$\to$device barrier lives;
    \item explain the two distinct roles of PRNG keys in this loop.
\end{itemize}
\end{objectives}

\begin{lstlisting}[style=py]
state        = replicate_state(state, devices=devices)
p_train_step = create_train_step(devices=devices)
p_eval_step  = create_eval_step(devices=devices)
train_iter, _ = get_datasets(config, num_devices=num_devices, seed=seed)

for epoch in range(config.epochs):
    for step in range(steps_per_epoch):
        batch        = next(train_iter)
        batch        = shard_batch(batch, num_devices)    # (N, B/N, ...)
        rng, step_rng = jax.random.split(rng)
        step_rngs    = jax.random.split(step_rng, num_devices)

        state, metrics = p_train_step(state, batch, step_rngs)

        step_loss = float(metrics["loss"][0])    # implicit host barrier
        step_acc  = float(metrics["accuracy"][0])

    test_metrics = _run_evaluation(state, p_eval_step, config, num_devices)
\end{lstlisting}

\begin{keypoint}[Four things to notice]
\begin{enumerate}
\item \textbf{One RNG per device.} \texttt{jax.random.split(step\_rng, num\_devices)} gives
      each device its own dropout stream. Without this, every device would apply identical
      dropout and regularisation strength would effectively halve.
\item \textbf{Asynchronous dispatch.} \texttt{p\_train\_step} returns lazy arrays immediately;
      compute runs on TPU in the background. The \texttt{float(...)} call is what blocks the
      host until the step is actually done.
\item \textbf{Metrics have a device axis.} \texttt{metrics["loss"]} has shape
      \texttt{(num\_devices,)}, every entry equal because of \texttt{pmean}. Indexing
      \texttt{[0]} just picks any one.
\item \textbf{Batch sharding is a numpy reshape.} It runs on the host and is effectively
      free compared to the $\sim$33 ms step.
\end{enumerate}
\end{keypoint}

\section{Experiment 1: scaling}
% =========================================================================

\begin{objectives}
\begin{itemize}[leftmargin=*, itemsep=1pt]
    \item define throughput, step time, and scaling efficiency formally;
    \item predict the shape of the efficiency curve given compute and communication costs;
    \item execute the scaling experiment on your own hardware and interpret the plots.
\end{itemize}
\end{objectives}

\subsection{What we are measuring}

For $k \in \{1, 2, 4, 8\}$ devices we measure:

\begin{itemize}
\item \textbf{Step time} $T_k$: median wall-clock time for one forward-backward-update cycle.
\item \textbf{Throughput} $\Theta_k = B_k / T_k$ images per second, where $B_k = k \cdot B_1$.
\item \textbf{Scaling efficiency} $\eta_k = \Theta_k / (k \cdot \Theta_1)$. Perfect scaling is
      $\eta = 1$.
\end{itemize}

\subsection{A simple model}

Let $C$ be per-step compute time and $R$ the all-reduce time on $k$ devices. Then
$$
T_k \approx C + R(k), \qquad \eta_k \approx \frac{C}{C + R(k)}.
$$
$R(k)$ grows slowly with $k$ on mesh topologies (logarithmically for ring all-reduce),
while $C$ is constant in per-device batch size. So $\eta_k$ decreases as $k$ grows.

\begin{predict}
You have a model where $C = 30$ ms per step and $R(k) = 3 \log_2 k$ ms.
Without running anything, compute $\eta_1, \eta_2, \eta_4, \eta_8$.
Then state in words: \emph{as $k$ doubles, does efficiency fall by a constant factor, a
constant amount, or something else?}
\answerspace[4]
\end{predict}

\subsection{Measurement hygiene}

\begin{enumerate}
\item \textbf{Warmup.} The first step compiles via XLA ($\sim$65\,s on v6e-8). We run 10
      untimed warmup steps before collecting numbers.
\item \textbf{Explicit block.} We call
      \texttt{jax.tree.map(lambda x: x.block\_until\_ready(), state)} after each timed step
      so the tick captures real device work, not dispatch latency.
\item \textbf{Device subset.} To benchmark a strict subset, we forward
      \texttt{devices=all\_devices[:k]} into \emph{both} \texttt{jax.pmap} \emph{and}
      \texttt{flax.jax\_utils.replicate}. Forgetting either leaves pmap defaulting to all
      local devices, and the sharded batch's leading dim mismatches.
\end{enumerate}

\begin{pitfall}[The \texttt{devices=} trap]
On a multi-device host (e.g. TPU v3-8), calling \texttt{jax.pmap(f)} without a
\texttt{devices=} argument locks in \emph{all} local devices. If you then pass a batch with
leading dim 4 while 8 devices are bound, you get a shape error. This project threads
\texttt{devices=} through every \texttt{pmap} and \texttt{replicate} call; other codebases
often don't.
\end{pitfall}

\begin{exercise}[Efficiency is bandwidth-bound, \stars{2}]

happens to $C$? What happens to $R(k)$ (recall: all-reduce traffic scales with parameter
count)? Does efficiency go up, down, or stay the same?
\answerspace[3]
\end{exercise}

\section{Experiment 2: straggler}
% =========================================================================

\begin{objectives}
\begin{itemize}[leftmargin=*, itemsep=1pt]
    \item explain why \texttt{time.sleep} cannot be used to simulate a straggler in JAX;
    \item predict step-time slowdown as a linear function of injected delay;
    \item connect the finding to production mitigations (async SGD, backup workers).
\end{itemize}
\end{objectives}

\subsection{The question}

A synchronous data-parallel system advances only as fast as its slowest worker. How much
does a single slow device hurt total throughput?

\subsection{Injecting a real straggler}

\texttt{time.sleep(x)} is useless here: it is a Python call, and Python does not run
\emph{inside} a pmap'd, JIT-compiled XLA program. Even if it did, a smart scheduler might
hide it behind other work. We need a delay XLA cannot elide --- real compute with a real
data dependency on itself:

\begin{lstlisting}[style=py]
device_idx = jax.lax.axis_index("batch")          # 0..num_devices-1

def _straggler(acc):
    def body(i, a): return a @ jnp.eye(64) + 0.0 * a
    return jax.lax.fori_loop(0, delay_iterations, body, acc)

def _no_delay(acc): return acc

dummy = jnp.ones((64, 64))
_ = jax.lax.cond(device_idx == 0, _straggler, _no_delay, dummy)
\end{lstlisting}

Each loop iteration multiplies a $64 \times 64$ matrix by the identity and adds $0 \cdot a$.
The data dependency on the previous \texttt{acc} prevents the compiler from constant-folding
or hoisting the loop out, and the \texttt{lax.cond} on \texttt{axis\_index("batch") == 0}
confines the work to device 0.

\begin{exercise}[Why \texttt{lax.cond} and not Python \texttt{if}? \stars{2}]
You might be tempted to write \texttt{if device\_idx == 0: <straggler>}. Explain why that
does not work inside a pmap'd function, and what \texttt{jax.lax.cond} does differently.
\answerspace[3]
\end{exercise}

\subsection{What to expect}

For baseline step time $T$ and injected extra time $\Delta$ on one device,
$$
T_{\text{straggler}} \approx T + \Delta, \qquad
\text{slowdown} = \frac{T_{\text{straggler}}}{T} \approx 1 + \frac{\Delta}{T}.
$$

\begin{predict}
Baseline $T \approx 33$ ms on 8 TPU v6e chips. Suppose injecting 1000 extra matmul
iterations on device 0 adds $\Delta \approx 10$ ms of extra compute on that device.
What slowdown factor do you expect?
If the answer were instead 5$\times$, what \emph{must} have been true about the injected
compute?
\answerspace[4]
\end{predict}

\begin{exercise}[Why this matters in production, \stars{1}]
Name three realistic sources of real stragglers in a production training cluster.
\answerspace[2]
\end{exercise}

\section{TPU specifics}
% =========================================================================

\begin{objectives}
\begin{itemize}[leftmargin=*, itemsep=1pt]
    \item explain why JAX installation differs between TPU and GPU hosts;
    \item describe what changes when you flip \texttt{jax\_default\_matmul\_precision} to bf16;
    \item identify the trade-off between spot and on-demand TPU VMs.
\end{itemize}
\end{objectives}

\subsection{Why JAX installs differently on TPU}

TPUs do not speak CUDA; they speak over \texttt{libtpu}, a Google-provided shared library
that plugs into JAX via a plugin.

\begin{pitfall}[Silent fallback to CPU]
If you run \texttt{pip install jax[cuda12]} on a TPU VM, JAX will import successfully but
fall back to CPU with \emph{no error message}. Your training will be tens of times slower
with zero warning. Always install from the TPU bucket:
\begin{lstlisting}[style=sh]
pip install -U "jax[tpu]>=0.4.20" \
    -f https://storage.googleapis.com/jax-releases/libtpu_releases.html
\end{lstlisting}
Our \texttt{setup.sh} detects TPU by looking at \texttt{/dev/accel*} and the \texttt{TPU\_NAME}
env var --- deliberately before JAX is installed, so it can pick the right wheel on a fresh VM.
\end{pitfall}

\subsection{bf16 on the MXU}

TPU v3 and v6e execute matmuls natively in bf16 (brain-float: 1 sign bit, 8 exponent bits,
7 mantissa bits). Enabling bf16 for matmuls while keeping fp32 parameters is one line:

\begin{lstlisting}[style=py]
jax.config.update("jax_default_matmul_precision", "bfloat16")
\end{lstlisting}

\begin{keypoint}[What \texttt{jax\_default\_matmul\_precision} does]
It does \emph{not} change parameter dtype or optimizer state. It tells XLA that every matmul
(Dense, attention QKV, einsum, Conv) can run the MXU in bf16 mode. Accumulation is still fp32.
On v6e this is typically a 1.5--2$\times$ throughput win for essentially free.
\end{keypoint}

\begin{exercise}[bf16 vs fp16, \stars{2}]
bfloat16 has the same exponent range as float32 but fewer mantissa bits. fp16 has the same
mantissa count as bfloat16 but a much smaller exponent range. Why does that make bf16 safer
for training than fp16, even though they have the same total bit width?
\answerspace[3]
\end{exercise}

\subsection{pmap vs pjit vs shard\_map}

This project uses \texttt{pmap} exclusively, because we only ever do \emph{pure data
parallelism}: the same model on every device. \texttt{pjit} (and its successor
\texttt{shard\_map}) is the right tool when you need \emph{tensor parallelism} (a single
layer split across devices) or \emph{pipeline parallelism}. Our ViT-Small fits in a single
TPU chip's HBM, so model parallelism would be gratuitous.

\subsection{Spot/preemption}

v6e-8 spot VMs cost roughly one third of on-demand ($\sim$\$1.26/hr vs \$4.21/hr) but can be
\emph{preempted} at any time: GCP reclaims the hardware, the VM transitions to
\texttt{PREEMPTED}, your process is gone. Mitigation in practice:
\begin{itemize}
    \item Use on-demand for long (overnight) runs.
    \item Use \texttt{gcloud alpha compute tpus queued-resources} to auto-retry until
          capacity returns.
    \item Checkpoint model state to Cloud Storage between epochs; any run that isn't
          checkpointed pays the ``preempted = start over'' tax.
\end{itemize}

\begin{exercise}[Economics, \stars{1}]
A 2-hour training run at v6e-8 spot is \$2.52. If the VM has a 20\% chance of being
preempted per run and you restart from scratch on preemption, what is the expected total
cost to complete the run? (Assume preemptions are memoryless.)
\answerspace[3]
\end{exercise}

\appendix
\section{Selected solutions}
% =========================================================================

\paragraph{Exercise 1.1 (per-device arithmetic).}
Each chip sees $512 / 8 = 64$ images per step. One epoch is
$\lfloor 50000 / 512 \rfloor = 97$ steps (the ragged tail is dropped).

\paragraph{Exercise 1.2 (first-step cost).}
XLA traces the pmap'd function, lowers it to HLO, runs passes, and compiles to a TPU
executable on the first call. The compiled graph is cached for the rest of the run, so
subsequent steps are $\sim$2000$\times$ faster.

\paragraph{Exercise 2.1 (token bookkeeping).}
$(64/4)^2 = 256$ patches. Including \texttt{[CLS]}, 257 tokens.

\paragraph{Exercise 3.1 (sharded shapes).}
\texttt{image} becomes \texttt{(8, 128, 32, 32, 3)};
\texttt{label} becomes \texttt{(8, 128)}.

\paragraph{Exercise 3.3 (why \texttt{copy()}).}
\texttt{\_augment\_batch} flips images in-place via \texttt{images[flip\_mask] = images[flip\_mask, :, ::-1, :]}.
Without \texttt{copy}, that mutation writes back into the original dataset array and the
augmentation becomes cumulative across epochs.

\paragraph{Exercise 4.1 (input/output shapes).}
Each device sees \texttt{(64, 128)}. The caller sees \texttt{(8, 64, 128)}.

\paragraph{Exercise 4.2 (forget pmean).}
Every device trains on its own slice with its own independent gradients. Eight different
parameter copies diverge. You're effectively running eight independent models that pretend
to share weights but don't; the training is meaningless.

\paragraph{Exercise 4.3 (NaN on one device).}
\texttt{pmean} averages, so \texttt{mean(finite, finite, ..., NaN) = NaN}. Every device
receives a NaN update, corrupting all copies of the parameters. This is why production
training almost always uses gradient clipping and NaN checks.

\paragraph{Exercise 5.2 (why split keys).}
If every device uses the same \texttt{step\_rng}, dropout masks are identical across
devices. Effectively you reduce the dropout noise seen by the model by a factor of
$\sqrt{N}$ --- the gradient estimate is averaged over $N$ \emph{correlated} samples, not
$N$ independent ones. You can detect this by measuring train loss variance across steps
with vs.\ without per-device keys.

\paragraph{Exercise 6.1 (efficiency is bandwidth-bound).}
$C$ scales roughly linearly with model size. $R(k)$ also scales with parameter count (all-reduce
traffic = number of parameters). Whether efficiency goes up depends on which grows faster;
typically for transformer-style models $C$ wins, so efficiency rises with model size.

\paragraph{Exercise 7.1 (lax.cond vs Python if).}
\texttt{device\_idx} inside pmap is a \emph{traced} JAX value, not a concrete Python int.
A Python \texttt{if} tries to branch on it at trace time and fails with \texttt{ConcretizationTypeError}.
\texttt{jax.lax.cond} compiles to a runtime branch inside the XLA program.

\paragraph{Exercise 8.1 (bf16 vs fp16).}
bf16's 8-bit exponent matches float32's range, so gradients don't underflow or overflow
during training. fp16's 5-bit exponent needs dynamic loss-scaling tricks to avoid underflow
on small gradients. bf16 essentially drops mantissa precision (which matmul accumulators
paper over); fp16 drops range, which is harder to compensate for.

\paragraph{Exercise 8.2 (preemption economics).}
Expected cost per attempt is \$2.52; expected number of attempts until success is $1/0.8 = 1.25$.
Expected cost is \$2.52 \emph{for the successful run} plus $0.2 \times \$2.52 \times \text{(expected attempts before success)} = 0.2/0.8 \times \$2.52 = \$0.63$
for the wasted preempted attempts. Total expected cost: \$3.15.
